Q1: What is Cluster Computing?
A: Cluster computing is a distributed computing paradigm where multiple independent
   computers (called nodes), connected through a high-speed local network or virtualized
   cluster, work together as a single unified system. It provides horizontal scalability
   (adding more machines) and high availability to process datasets that exceed the RAM
   and compute capacity of any single machine.

Q2: What is the difference between Vertical Scaling and Horizontal Scaling?
A: - Vertical Scaling (Scale-Up): Adding more CPU, RAM, or SSD to a single existing
     computer. It has hard physical limits and becomes extremely expensive.
   - Horizontal Scaling (Scale-Out): Adding more commodity machines (nodes) to a
     cluster. Apache Spark and Hadoop are designed specifically for horizontal scaling.

Q3: Why did you choose Apache Spark over Hadoop MapReduce?
A: 1. Speed: Spark is up to 100x faster in memory and 10x faster on disk than MapReduce.
   2. In-Memory Processing: MapReduce writes all intermediate outputs to physical disk
      (HDFS) between map and reduce phases. Spark keeps intermediate data in RAM
      using Resilient Distributed Datasets (RDDs) and DataFrames.
   3. Execution Engine: Spark uses a Directed Acyclic Graph (DAG) optimizer that
      chains operations and minimizes data shuffling, whereas MapReduce strictly
      enforces a 2-stage Map -> Reduce paradigm.
   4. Rich Ecosystem: Spark has built-in Spark SQL, Spark MLlib, Spark Streaming,
      and GraphX in a single framework.

Q4: What is PySpark, and how does it interact with Apache Spark?
A: PySpark is the Python API for Apache Spark. Apache Spark itself is written in Scala
   and runs on the Java Virtual Machine (JVM). PySpark uses an inter-process bridge
   called Py4J. The Python driver program communicates with a JavaSparkContext in the
   JVM. When distributed operations run, tasks are executed by worker JVMs. Data is
   serialized between Python and Java using Py4J.

Q5: What does execution master `local[*]` mean?
A: In Apache Spark, `local[*]` runs Spark in local mode on a single machine, where the
   asterisk `[*]` instructs Spark to spawn as many worker executor threads as there are
   logical CPU cores on the host machine. On my laptop, it utilized all available CPU
   cores in parallel. It simulates cluster behavior locally without requiring physical
   multi-node networking.

Q6: What is the difference between RDD, DataFrame, and Dataset in Spark?
A: - RDD (Resilient Distributed Dataset): The fundamental, low-level abstraction in
     Spark. It is an immutable, lazily evaluated, partitioned collection of raw Java/Python
     objects. It provides fault tolerance via lineage graphs, but lacks schema metadata
     and Catalyst query optimization.
   - DataFrame: A distributed collection of data organized into named columns (like a
     SQL table). It includes schema metadata and is automatically optimized by Spark's
     Catalyst Optimizer and Tungsten execution engine. We used DataFrames in this project.
   - Dataset: An extension of DataFrames with compile-time type safety, available in
     Scala and Java. In Python (PySpark), DataFrames and Datasets are unified because
     Python is dynamically typed.

Q7: What is Lazy Evaluation in Apache Spark? Why is it useful?
A: Lazy evaluation means Spark does NOT execute computations immediately when you define
   them. Instead, Spark simply records the sequence of operations as a Directed Acyclic
   Graph (DAG) of logical transformations.
   Execution only starts when an "Action" (such as .count(), .collect(), or .write) is called.
   Benefit: It allows the Catalyst Optimizer to analyze the entire workflow, prune unused
   columns, push down filters, and combine operations to create the fastest physical plan.

Q8: What is the difference between a Transformation and an Action?
A: - Transformation: A lazy operation that takes a DataFrame/RDD and returns a new
     DataFrame/RDD. No actual computation happens. Examples: .filter(), .select(),
     .withColumn(), .groupBy(), .repartition(), .dropDuplicates().
   - Action: An eager operation that triggers DAG execution and returns a non-DataFrame
     result to the driver program or writes data to storage. Examples: .count(),
     .collect(), .show(), .take(), .write.csv(), .save().

Q9: What is the difference between Narrow and Wide Transformations?
A: - Narrow Transformation: Each input partition contributes to only ONE output partition.
     Data does not need to move across the network or worker cores. Examples: .filter(),
     .select(), .withColumn(). These execute fast within the same stage.
   - Wide Transformation: Multiple input partitions contribute to multiple output partitions.
     Data must be redistributed across cores or nodes. This process is called SHUFFLING.
     Examples: .groupBy(), .orderBy(), .distinct(), .repartition(), .join().
     Wide transformations define stage boundaries.

Q10: What is Shuffling in Spark and why is it expensive?
A: Shuffling is the physical redistribution of data across partitions, cores, or cluster
   nodes during wide transformations. It is the most expensive operation in cluster
   computing because it involves:
   1. Serializing data from memory to disk.
   2. Network transmission between nodes (or inter-thread copying).
   3. Deserializing data and sorting/merging it in memory.
   Minimizing shuffles is the #1 optimization rule in Spark.

Q11: What is a Partition in Spark?
A: A partition is a logical, atomic chunk of a distributed dataset. Partitions represent
   the fundamental unit of parallelism: one executor task processes exactly one partition
   at any given moment. For example, if you have 8 partitions and 8 CPU cores, all 8 tasks
   run simultaneously in parallel.

Q12: What is the difference between `repartition()` and `coalesce()`?
A: - `repartition(k)`: Forces a full, round-robin shuffle of all data across all partitions
     to produce exactly k evenly distributed partitions. Can increase or decrease partitions.
     Incurs high shuffle cost.
   - `coalesce(k)`: Merges existing adjacent partitions locally without triggering a full
     shuffle. It can ONLY decrease partitions (e.g., from 8 to 2). It is much faster
     than repartition for down-scaling.

Q13: How does Spark achieve Fault Tolerance?
A: Spark achieves fault tolerance through RDD/DataFrame LINEAGE (the DAG). Instead of
   duplicating all data in memory across nodes, Spark remembers the exact recipe
   (transformations) used to compute each partition from the base data. If an executor
   crashes and loses partition #3, Spark simply re-executes the lineage graph for
   partition #3 only on another surviving core or node.

Q14: What is the Spark Catalyst Optimizer?
A: The Catalyst Optimizer is Spark SQL's query optimization engine. It takes logical
   DataFrame queries and passes them through four stages:
   1. Analysis: Resolves column names and table references against a catalog.
   2. Logical Optimization: Applies rules like predicate pushdown (filtering early)
      and column projection pruning (discarding unused columns).
   3. Physical Planning: Generates multiple physical execution plans and picks the
      one with the lowest estimated cost (e.g., choosing BroadcastHashJoin vs SortMergeJoin).
   4. Code Generation (Tungsten): Generates highly efficient Java bytecode on the fly
      using Whole-Stage Code Generation.

Trap Q3: "Why did you care about PR-AUC when ROC-AUC was already 0.8393?"
Your Answer: "Our target variable has a 67:33 class imbalance. In imbalanced datasets,
ROC-AUC can be overly optimistic because its False Positive Rate includes True Negatives
(the majority class). Even if false positives increase, a large number of True Negatives
keeps FPR low.
PR-AUC (Precision-Recall AUC) does NOT include True Negatives at all. It focuses solely
on the minority class. Our PR-AUC of 0.8968 confirms that the model maintains high
precision across different recall thresholds for the minority Rejected class."

Trap Q4: "What happens if a worker executor crashes during execution?"
Your Answer: "Spark handles this gracefully via RDD Lineage. The Driver program maintains
the DAG. If worker node #2 crashes, the Driver detects the heartbeat loss, marks the
executor dead, and re-schedules only the missing tasks and partitions on another surviving
worker core or node. The entire job does NOT restart from scratch."

Trap Q5: "What is `spark.sql.shuffle.partitions`? What is its default value?"
Your Answer: "The default value in Apache Spark is 200. This means whenever a wide
transformation (like groupBy or join) occurs, Spark shuffles data into 200 partitions.
For a small or medium dataset on a local machine, 200 partitions creates excessive task
scheduling overhead because each partition only contains a tiny handful of rows. In our
project configuration (`src/config.py`), we explicitly tuned `spark.sql.shuffle.partitions`
to 4 and 8, matching our core count and drastically improving local performance."

Trap Q6: "Why is `df.collect()` dangerous on big data?"
Your Answer: "`df.collect()` retrieves ALL records from all distributed worker nodes
and pulls them into the Driver program's single JVM memory. If the dataset has 100 million
records (say 50 GB), pulling it into a 4 GB Driver RAM will immediately crash the application
with a `java.lang.OutOfMemoryError`. Instead of `collect()`, we should use actions like
`.take(n)`, `.show(n)`, or write directly to distributed storage with `.write.parquet()`."

Trap Q7: "What is Py4J overhead? Is Scala Spark faster than PySpark?"
Your Answer: "For standard DataFrame operations, PySpark has almost ZERO overhead compared
to Scala because the DataFrame API compiles to the same Catalyst physical execution plan
inside the JVM.
However, if you write custom Python UDFs (User-Defined Functions), Spark has to serialize
data out of the JVM into a Python worker process, execute the Python code, and serialize
it back into the JVM. This causes serialization overhead. That is why I used native Spark
SQL functions (`pyspark.sql.functions`) for all feature engineering, keeping all execution
inside the optimized JVM."

Trap Q8: "What is the difference between a Driver and an Executor?"
Your Answer:
- Driver: The master process that runs your `main()` program. It creates the `SparkSession`,
  converts user code into a DAG, analyzes and optimizes the logical plan, breaks jobs into
  stages and tasks, and schedules tasks onto executors.
- Executor: Worker processes running on cluster nodes. They execute individual tasks
  assigned by the driver, perform computations, store cached partitions in RAM/disk, and
  send status and results back to the driver.

Trap Q9: "Why did you use VectorAssembler?"
Your Answer: "Spark MLlib algorithms (like LogisticRegression and RandomForestClassifier)
do not accept multiple independent columns as inputs like Scikit-Learn does. They expect
all predictor features to be packed into a single column containing a unified Vector object.
`VectorAssembler` is the Spark transformer that merges numerical columns, boolean flags,
and one-hot encoded vectors into that single required `features` vector column."

Trap Q10: "What is Data Skewness in Spark and how do you handle it?"
Your Answer: "Data skew occurs when data is partitioned unevenly, causing one partition
to hold 80% of the records while other partitions hold only 5%. This causes the 'straggler
problem', where 7 CPU cores finish in 1 second, but 1 core takes 2 minutes.
We handle data skew by:
1. Salting: Adding random prefixes to the join/group key to spread records evenly.
2. Using `.repartition()` on a high-cardinality column.
3. Using Broadcast Joins (`broadcast(df)`) when joining a large DataFrame with a small one."

Trap Q11: "What is the difference between `cache()` and `persist()`?"
Your Answer:
- `df.cache()`: Stores the DataFrame in memory with the default storage level `MEMORY_AND_DISK`
  (deserialized in memory, spills to disk only if memory is full).
- `df.persist(StorageLevel)`: Gives you granular control over where data is stored. You can
  specify `MEMORY_ONLY`, `MEMORY_ONLY_SER` (serialized in RAM to save space), `DISK_ONLY`,
  or replicated across nodes (`MEMORY_AND_DISK_2`).
- In short: `cache()` is simply `persist()` with the default storage level.

Trap Q16: "What is Broadcast Join in Spark?"
Your Answer: "When joining a large DataFrame (100 GB) with a small DataFrame (10 MB),

Spark copies the small DataFrame to the RAM of every worker node. Each worker then
performs a local hash join without any network shuffling of the large DataFrame.
It is invoked using `pyspark.sql.functions.broadcast(small_df)`."

Trap Q17: "What is Whole-Stage Code Generation in Spark Tungsten?"

an entire chain of pipeline stages into a single optimized Java function, compiling it
to raw bytecode at runtime. This eliminates virtual function dispatch overhead, keeps
data in CPU L1/L2 caches, and drastically boosts execution speed."

proper quoting of strings containing commas, standard CRLF line breaks, and consistent
encoding (UTF-8). This guarantees that Spark's distributed CSV reader parses columns
cleanly without row-boundary corruption across split partitions."

SECTION 5: RAPID-FIRE ONE-LINER DEFINITIONS (FLASHCARDS)
================================================================================

1.  DAG (Directed Acyclic Graph): A graph of sequential computation stages with no loops.
2.  Driver: The master process coordinating Spark execution and task scheduling.
3.  Executor: The worker process executing tasks and caching data partitions.
4.  Task: The smallest unit of execution in Spark, run on a single partition.
5.  Stage: A group of tasks that can execute in parallel without a data shuffle.
6.  Job: A sequence of stages triggered by an Action.
7.  Narrow Dependency: Child partition depends on only one parent partition (No shuffle).
8.  Wide Dependency: Child partition depends on multiple parent partitions (Requires shuffle).
9.  Py4J: The gateway bridge allowing Python to call Java methods in the Spark JVM.
10. Catalyst: Spark SQL's rule-based and cost-based query optimizer.
11. Tungsten: Spark's in-memory execution engine optimizing hardware CPU and memory.
12. VectorAssembler: Feature transformer combining raw columns into a single feature vector.
13. StringIndexer: Encodes string labels into category index numbers (0.0, 1.0, 2.0).
14. OneHotEncoder: Maps categorical index numbers to binary sparse vectors.
15. StructType: Explicit programmatic schema definition for Spark DataFrames.
16. Predicate Pushdown: Catalyst optimization that filters data before loading/joining.
17. Broadcast Variable: Read-only variable cached on every worker node to avoid re-sending.
18. Accumulator: Write-only shared variable used for distributed counters and metrics.
19. ROC-AUC: Area under the Receiver Operating Characteristic curve (Discrimination power).
20. PR-AUC: Area under the Precision-Recall curve (Best for imbalanced target classes).
